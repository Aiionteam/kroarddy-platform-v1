ScamX 기술 보고서

1. 문서 소개

이 문서는 ScamX 프로젝트의 기획 배경, 기술적 의사결정, Android 정책 대응, AI 파이프라인 설계, 개인정보 보호 전략, 그리고 실제 개발 과정에서 겪었던 문제와 해결 과정을 정리한 기술 보고서입니다.

ScamX는 단순한 스팸 필터가 아니라, 문자 내용을 의미 기반으로 분석해 신종 스캠까지 탐지하는 실시간 보안 앱을 목표로 설계했습니다.

2. 프로젝트 개요

ScamX는 Android 환경에서 스캠 문자를 실시간으로 탐지하기 위해 기획한 개인 프로젝트였습니다. 기획부터 백엔드, 프론트엔드, 모바일 개발, AI 파이프라인 설계까지 전 과정을 직접 진행했습니다.

핵심 목표는 다섯 가지로 정리했습니다.

- 통신사 필터링으로 잡히지 않는 가족·지인 사칭형 스캠을 탐지하는 것
- 패턴 기반이 아닌 의미 기반으로 스캠을 분석하는 것
- Android 10 이상 정책을 준수하는 합법적 문자 수집 구조를 만드는 것
- 개인정보를 저장하지 않는 비식별화 AI 분석 구조를 설계하는 것
- 사용할수록 정확도가 올라가는 Self-Improving 시스템을 만드는 것

3. 문제 인식

ScamX를 만들게 된 가장 큰 이유는 기존 스팸 탐지 방식의 한계를 직접 체감했기 때문이었습니다.

- 통신사 스팸 필터는 발신번호 기반이라 저장된 번호로 위장한 스캠을 제대로 잡지 못했습니다.
- 기존 보안 앱들은 패턴 DB 매칭 방식에 의존하는 경우가 많아 신종 스캠에 취약했습니다.
- Android 10 이후에는 SMS 브로드캐스트 방식이 제한되면서 문자 본문을 직접 읽는 구조를 그대로 사용할 수 없었습니다.
- 고령층은 스캠에 더 취약한데도, 기존 앱은 사용성이 복잡해 실제 대응이 쉽지 않았습니다.

이 문제들을 풀기 위해서는 문자 내용을 단순 키워드가 아니라 의미적으로 분석하는 보안 앱이 필요하다고 판단했습니다.

4. Android 정책 대응

초기에는 일반적인 보안 앱처럼 SMS 브로드캐스트로 본문을 읽는 방향을 먼저 검토했습니다. 하지만 Android 10 이후 Google 정책이 강화되면서, 메시지 앱보다 먼저 SMS 본문을 읽는 방식은 현실적으로 유지하기 어려웠고 정책 이슈와 개인정보보호 이슈를 동시에 안게 되었습니다.

그래서 ScamX는 Notification Listener 기반으로 문자 관련 알림에서 본문을 수집하는 방식을 채택했습니다. 이 방식은 사용자 권한 범위 안에서 동작하도록 설계했고, Android 10 이상 환경에서도 비교적 일관되게 구현했습니다.

5. 개인정보 보호 설계

문자 관련 데이터를 서버로 전송하는 구조였기 때문에, 초기 설계부터 원문을 영구 저장하지 않는 것을 원칙으로 잡았습니다.

ScamX에서는 다단계 마스킹·비식별화 파이프라인을 적용했습니다.

- 서버에 도착하는 즉시 원문을 마스킹했습니다.
- 전화번호는 해시 처리했습니다.
- 계좌번호와 이름 등은 패턴 기반으로 마스킹했습니다.
- 민감 단어는 제거하거나 대체했습니다.
- AI 분석 후 사용자에게는 판단 결과 위주로만 전달했습니다.
- DB에는 원문 대신 비식별화된 의미 표현, 예를 들면 임베딩 벡터 같은 정보만 저장하도록 설계했습니다.

결국 서버에는 문자 자체가 아니라 분석에 필요한 의미 정보만 남도록 구성했습니다.

6. 아키텍처 개요

전체 구조는 다음과 같이 정리했습니다.

- 모바일: Kotlin 기반 Android 앱, Notification Listener로 문자 알림 수집
- 백엔드: Python, FastAPI, LangGraph 기반 AI 파이프라인
- AI 모델: KOLLECTRA, Sentence Embedding, LLaMA 3.1 8B, GPT-5 계열 경량 모델
- 데이터베이스: PostgreSQL, Neon, pgvector
- 프론트엔드: Next.js 기반 공공기관용 어드민 페이지

7. AI 파이프라인 설계

7.1 KOLLECTRA 1차 스캠 필터링

SMS 알림을 수신하면 가장 먼저 KOLLECTRA가 동작하도록 설계했습니다. 경량 Transformer 모델로 스캠과 정상 확률을 빠르게 계산했고, 정상으로 판단한 메시지는 이 단계에서 바로 종료시켰습니다. 이 단계 덕분에 불필요한 LLM 호출을 상당히 줄였습니다.

7.2 Sentence Embedding 의미 벡터 생성

KOLLECTRA가 의심으로 분류한 메시지는 임베딩 단계로 넘겼습니다. 문장을 768~1024차원 수준의 의미 벡터로 변환한 뒤, pgvector에 저장한 기존 스캠 벡터와 유사도를 비교했습니다. 스캠은 문구만 조금씩 바뀐 채 반복되는 경우가 많았기 때문에, 의미 기반 비교가 꼭 필요했습니다.

7.3 LLaMA 3.1 8B 의미 기반 스캠 분석

유사도만으로 결론을 내기 어려운 문장은 LLaMA가 문맥을 포함해 해석하도록 했습니다. 단순 패턴이 아니라 상황과 표현의 흐름까지 보게 하여 판단 정확도를 높이려 했습니다.

7.4 GPT-5 계열 경량 모델 신종 스캠 정밀 분석

LLaMA만으로 결론을 내리기 어려운 경우에만 상위 모델을 호출해 신종 스캠을 정밀 분석하도록 구성했습니다. 이 결과는 마스킹과 비식별화 과정을 거친 뒤 DB에 반영했고, 이후 비슷한 사례는 더 앞단 계층에서 처리하도록 Self-Improving 구조로 설계했습니다.

8. 전체 파이프라인 흐름

전체 흐름은 다음과 같았습니다.

SMS 알림 수신
→ KOLLECTRA 1차 필터링
→ Sentence Embedding 생성
→ pgvector 유사도 검색
→ LLaMA 의미 분석
→ 필요 시 GPT 계열 모델 정밀 분석
→ 결과 마스킹 후 DB 저장
→ 사용자 알림

9. UX 설계와 고령층 고려

테스트 과정에서는 고령층 사용자가 알림을 놓치는 문제가 반복적으로 나타났습니다. 그래서 기능 정확도만이 아니라, 실제로 위험을 인지하게 만드는 경험 설계도 중요하다고 판단했습니다.

적용한 UX 개선은 다음과 같았습니다.

- 알림이 상단바에 일정 시간 유지되도록 구성했습니다.
- 알림 센터에서 다시 확인할 수 있게 했습니다.
- 알림을 누르면 상세 분석 화면으로 이동하도록 연결했습니다.
- 이후에는 알림 지속 시간 같은 옵션도 확장할 수 있도록 고려했습니다.

고령층 사용자가 한 번 놓치더라도 다른 경로에서 다시 확인할 수 있게 만드는 데 중점을 두었습니다.

10. 개발 과정에서 가장 어려웠던 점

ScamX 개발에서 가장 어려웠던 부분은 단순 구현보다도 정책과 현실적인 제약을 동시에 만족시키는 일이었습니다.

- Android 10 정책 때문에 기존 SMS 수집 방식 대부분이 더 이상 유효하지 않았습니다.
- 개인정보보호 이슈 때문에 서버와 파이프라인 구조를 처음부터 다시 설계해야 했습니다.
- LLM 비용이 예상보다 커서 단계형 파이프라인을 여러 번 다시 조정했습니다.
- 스캠 문구는 계속 바뀌기 때문에 단순 패턴 매칭만으로는 한계가 분명했습니다.

이 과정을 거치면서 Notification Listener 기반 수집, KOLLECTRA → 임베딩 → LLaMA → GPT 계열 모델 구조, 그리고 의미 벡터 기반 Self-Improving 설계가 점차 완성되었습니다.

11. 성과 및 차별점

ScamX의 성과와 차별점은 다음과 같이 정리했습니다.

- LLM 호출을 최소화하는 구조로 API 비용을 크게 줄였습니다.
- 신종 스캠 사례를 의미 벡터와 DB에 누적해, 매번 전면 재학습 없이도 점진적으로 정확도를 높이도록 설계했습니다.
- Android 10 이상 정책 흐름에 맞춘 수집 구조를 설계했습니다.
- 공공기관 연동을 염두에 둔 어드민 페이지까지 함께 구상했습니다.
- 고령층도 알림 한 번으로 위험 여부를 직관적으로 인지할 수 있는 UX를 지향했습니다.

12. 한 줄 정리

의미 기반 분석으로 신종 스캠까지 탐지하는 실시간 AI 스캠 탐지 앱이라는 점이 ScamX의 핵심이었습니다.

이 문서는 사용자 초안을 바탕으로 표현과 문장 흐름을 다듬어 정리했습니다. 모델명, 비용 수치, 정책 해석은 실제 출시와 심의 기준에 맞춰 최종 검증이 필요했습니다.
