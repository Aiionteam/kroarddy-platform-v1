# planer.kroaddy.site — Standard 플래너 트러블슈팅 메모

`backend/planer.kroaddy.site`의 AI 일정·루트 파이프라인을 만들면서 겪은 이슈와, 그에 따른 설계·구현 방향을 정리한 문서이다. (회고 / 운영 참고용)

---

## 1. 좌표: Gemini 생성 → 카카오맵 검증 기반으로 전환

**당시 문제**

- 일정 JSON에 **위도·경도·주소까지 LLM이 채우도록** 두면, 문맥상 그럴듯하지만 **실제 지도와 맞지 않는 좌표**가 나오는 경우가 잦았다.
- 모델은 “검색 가능한 상호”와 “정확한 WGS84 좌표”를 같은 신뢰도로 쓰기 어렵고, hallucination이 좌표에 그대로 반영되기 쉽다.

**대응**

- 좌표·주소의 **단일 소스 오브 트루스**를 외부 지도 API로 두는 쪽으로 바꾼다.
- **카카오 키워드 검색(POI)** 등으로 장소명을 실제 POI와 매칭하고, 필요 시 **네이버 지오코딩**으로 보강하는 **검증·보강 파이프라인**으로 정리한다.
- LLM에는 “좌표를 만들지 말라”는 쪽으로 스키마·프롬프트를 단순화하고, 후처리에서만 좌표를 붙인다.

**요지**: 지리 정보는 **생성 모델이 아니라 지도 서비스**가 담당하는 것이 재현성과 사용자 신뢰 면에서 유리하다.

## 2. 다일차 생성: 1일차·2일차… 여러 번 호출 → 한 번에 N일차 생성으로 바꾼 배경

**당시 문제 (다회 호출 구조)**

- 1일차 생성 → 2일차 생성처럼 **호출을 나누면**, 각 호출이 **이전 일차 전체 맥락**을 충분히 반영하지 못하는 경우가 있었다.
- 그 결과 **이미 넣었던 일정과 거의 같은 코스를 또 추가**하거나, **일차 간 중복·맥락 단절**이 나는 버그가 반복되었다.
- “이전 대화/이전 JSON 전체”를 매번 완전히 넣지 않거나, 토큰 한도로 잘리면 **모델 입장에서는 1일차가 흐릿해지고** 같은 추천을 다시 내기 쉽다.

**대응 방향**

- **한 번의 요청으로 N일치 일정 JSON**을 받는 방식으로 바꿔, **여행 전체 기간·규칙·루트 테마**가 같은 프롬프트 안에 남도록 했다.
- 목적은 **“맥락이 끊기지 않게”** 하고, **동일 일정 중복 추가**를 줄이는 것이었다.

**트레이드오프 (알아두면 좋은 점)**

- 원샷 N일 생성은 **응답 길이·JSON 파싱 실패 위험**, **일자별 권역 분산·장소 중복 금지** 같은 규칙을 한 번에 지키기 어렵다는 부담도 있다.
- 이후에는 **일차별 순차 생성 + 이전 일차 장소를 exclude로 누적**하는 식으로, “맥락 유지”와 “규칙 준수”를 동시에 잡는 하이브리드로 발전시키는 경우가 많다. (저장소의 `graph.py` 주석·`nodes_schedule.py`의 순차 루프가 그 방향을 반영한다.)

## 3. 503·재시도·폴백과 “맥락 유실”

**현상**

- 생성 도중 **503(UNAVAILABLE)** 이 나오면, 클라이언트/게이트웨이 쪽에서 **재시도·타임아웃**이 걸리거나, 서버 로직에서 **다른 Gemini 모델로 폴백**하는 경로가 동작할 수 있다.
- 연결이 **끊겼다가 이어지는** 경우, 사용자 세션 관점에서는 **“한 번에 이어지는 한 번의 생성”**이 아니라 **여러 조각**으로 느껴질 수 있다.

**맥락과의 관계**

- 중간에 실패하면 **같은 스레드의 연속 completion**이 아니라 **새 요청**에 가까워지고, 앞단에서 넣어 주던 **장소 후보·금지 목록·일차별 힌트**가 빠지거나 줄면 모델은 다시 **1일차 위주의 안전한 답**으로 돌아가기 쉽다.
- 폴백으로 **모델 가중치가 바뀌면** 이전 호출과 **문체·추천 성향**이 달라져, 사용자가 보기에도 “앞내용과 안 맞는다”로 인식될 수 있다.

**대응 아이디어 (운영·설계)**

- 가능한 한 **짧은 프롬프트 + 상태를 서버 state에 고정**해, 재시도 시에도 **exclude 리스트·이미 확정된 일차 JSON**을 다시 주입한다.
- 503은 **Google 쪽 가용성** 이슈가 큰 경우가 많으므로, **프리뷰 모델만 쓰지 않고** 안정 구간 모델을 두는 것, **입력 토큰을 줄이는 것**이 재시도·폴백 빈도를 줄이는 데 도움이 된다.

## 4. 한 줄 요약

| 주제 | 핵심 |
|------|------|
| 좌표 | LLM 생성 신뢰 한계 → **카카오(및 네이버) 검증·지오코딩**으로 이전 |
| 다일차 호출 | 분할 호출 시 **맥락 단절·중복 일정** → **원샷 N일** 등으로 맥락 유지 시도 (이후 규칙 강화를 위해 순차+exclude 등으로 보완 가능) |
| 503 / 폴백 | **재시도·모델 전환·연결 끊김**이 **맥락 유실**과 겹치기 쉬움 → state 재주입·입력 경량화가 중요 |

1. 웹 맥락 수집 (60.14s) – "정보 검색의 과부하"
현상: nodes_schedule에서 뉴스, 날씨, 웹검색 등을 수집하는 데만 정확히 1분이 걸렸습니다.

원인: * 직렬 처리: 행사, 뉴스, 날씨, 구글 검색을 하나씩 순서대로 호출하고 있을 확률이 높습니다. 하나라도 응답이 늦으면 전체가 밀립니다.

방대한 검색량: 웹 맥락 데이터가 2636자나 됩니다. 검색 엔진에서 결과를 긁어오고 파싱하는 과정 자체가 무겁습니다.

해결책: asyncio.gather를 사용해 모든 검색 작업을 **병렬(Parallel)**로 돌려야 합니다. 60초를 15~20초로 단축할 수 있는 구간입니다.

2. Gemini 503 에러와 재시도 (약 82s 추가 지연) – "인프라 밀당"
현상: 02:09:32에 시작된 Day 1 생성이 02:11:05에 끝났습니다. (총 93초 소요)

원인: * 중간에 503 Service Unavailable이 두 번 떴습니다.

재시도 로직(nodes_common)이 3초 간격으로 설정되어 있는데, 구글 서버가 복구되기도 전에 너무 빨리 다시 찌른 감이 있습니다.

결국 3회차 시도 끝에 성공하면서, 순수 생성 시간 외에 재시도 대기 시간 + 중복 호출 시간이 통째로 낭비되었습니다.

해결책: **Exponential Backoff(지수 백오프)**를 도입하세요. 서버가 바쁠 땐 조금 더 여유를 두고 찔러야 오히려 더 빨리 성공합니다.

Day 2: 56s

원인: 현재 구조가 "Day 1 다 만들고 나서 → 좌표 보정하고 → 그 결과 들고 Day 2 시작" 하는 방식입니다. 각 날짜가 앞선 날짜의 결과에 의존적이라 병렬화가 안 되어 있습니다.

독립적 프롬프팅: 날짜 간 의존성을 최소화하여 Day 1, 2, 3를 동시에 생성(Parallel Generation)한 뒤 마지막에 합치는 구조를 고려해 보세요.
